# Planning & Design Decisions

Prepaid CX — Ticket Trend Analysis (technical assignment).

This document records **what was built, why each choice was made, what was
traded away, and what was deliberately left out**. It was written before
implementation and updated as decisions changed; the decision log at the end
shows the order things were decided in, including reversals.

---

## 1. Goal, as the assignment frames it

> "The volume numbers are the easy part. What we care about is whether you can
> separate noise that already has a known cause from signal that needs
> escalating, and whether you say so clearly to someone who will never read your
> code."

The scoring weight is on **judgment and communication**, not on volume of code.
Every decision below is weighed against that:

1. Correct, explainable SQL (Part 1, 30%).
2. A small, tested API with an anomaly rule we can defend (Part 2, 30%).
3. Note classification that does *not* trust the agent label, and an executive
   brief generated by the pipeline (Part 3, 40%).

Hard constraints from the brief: runs on a laptop, SQLite or DuckDB only, no DB
server, no cloud, no paid API; README gets a reviewer running in < 10 minutes.

Exploration was done with ad-hoc SQL over the four CSVs. `true_labels.csv` was
**not opened** (see §4.1).

| # | Observation | Interpretation |

## 3. Architecture

```
take-home-project/
├── pom.xml, mvnw              # reviewer only needs JDK 25
├── data/                      # tickets, ticket_notes, network_incidents, region_base
├── src/main/java/dev/cxtrends/
│   ├── db/        Csv, SqlScript, DataLoader (CSV → cx.db on every start)
│   ├── trends/    TrendController, TrendService, TrendRepository, AnomalyDetector, Incident
│   ├── classify/  NoteNormalizer, Taxonomy, OllamaClient, TopicClassifier, ClassificationReport
│   ├── brief/     BriefFactsBuilder (the judgment), BriefTemplate, BriefWriter, NumberGuard
│   └── cli/       CommandRunner, QueriesCommand
├── src/main/resources/
│   ├── sql/schema.sql         # tables, indexes, ticket_topics view
│   ├── sql/queries.sql        # Part 1 answers (run by the app or the sqlite3 CLI)
│   └── static/index.html      # optional chart over /trends
├── review/topic_review.csv    # human labels for the 91 texts
├── output/                    # generated + committed
│   ├── queries/Q*.csv
│   ├── note_topics_llm.csv    # model output cache
│   ├── classification_report.md
│   ├── brief_facts.json       # every number the brief may use
│   └── cx_brief.md            # the executive brief
└── docs/  PLANNING.md, experiments/
```

One Spring Boot jar, several entry points:

| Command | Needs Ollama? | Does |
|---|---|---|
| *(none)* | no | `GET /trends` on :8080, chart at `/` |
| `load` | no | rebuild `cx.db` and exit |
| `queries` | no | run `src/main/resources/sql/queries.sql`, print, write `output/queries/` |
| `classify` | only for texts missing from the cache | refresh `note_topics_llm.csv`, write the disagreement report |
| `brief` | optional (template fallback) | compute facts, write `cx_brief.md` |

Every start rebuilds `cx.db` from `data/` (~1 s), so the database can never be
stale relative to the CSVs. Every generated artefact is committed, so a reviewer
**without Ollama** can still run everything and read every output.

## 4. Decisions, alternatives and trade-offs

### 4.1 `true_labels.csv` is not used at all

The file maps every ticket to a `true_category`. The assignment lists four files;
this is a fifth, and it is almost certainly the grader's answer key for Part 3a.

- **Decision:** not loaded, not used for training, prompt-tuning or evaluation;
  excluded via `.gitignore`. Mentioned openly in the README.
- **Trade-off:** no "accuracy against ground truth". Instead, all 91 base texts
  are human-reviewed (§4.6), which is what a team would do in reality.

### 4.2 Assignment choice: CX Ticket Trend (Project 2) over Recharge Insight (Project 1)

| | Project 1 (Recharge + RAG) | Project 2 (CX trends) |
|---|---|---|
| Differentiation | Low: most candidates produce similar RAG + CRUD | High: open-ended, rewards judgment |
| Telco relevance | Medium | High: signal vs outage triage is daily CX/NOC work |
| Risk | Low | Higher (ambiguous success criteria) |

Time was not the binding constraint, so we chose the one with more room to show
judgment.

### 4.3 Language and versions: Java 25 (LTS), Spring Boot 4.1.2, Maven 3.9.16

- **Java:** the author's primary language (defensible line by line in the
  follow-up) and the dominant language at the hiring company.
  **Rejected:** Python (best ML ecosystem, but not the author's main language and a
  second toolchain for the reviewer); Go (second language); a Java/Go + Python
  split (two toolchains, which works against the 10-minute setup).
- **Versions:** the latest stable at the time of writing, checked against Maven
  Central / Adoptium on 2026-10-26. Java **25** is the latest LTS; 27 is newer but
  non-LTS and less likely to be on a reviewer's machine. Spring Boot **4.1.2** is
  the latest GA (4.2 was still RC). Maven **3.9.16** comes through the wrapper.
  3.10.0 was tried first, but IntelliJ 2025.3 cannot import a project built
  with it (its embedded Maven server fails with a Guice `ArtifactHandlerManager`
  error), so every dependency showed as unresolved. 3.9.16 is the newest
  release that IDEs import cleanly, and Maven 4 was still RC.
- **Trade-off:** no pandas / scikit-learn. That is acceptable: SQL does the
  analytics, and only 91 texts need classifying, so plain HTTP to Ollama is enough.
- **Reviewer mitigation:** the PDF hints at Python (`pip install duckdb`), so the
  README states the JDK 25 prerequisite first and ships `./mvnw`.

### 4.4 Database: SQLite (embedded via `sqlite-jdbc`)

*Originally planned as DuckDB; switched to SQLite at the author's request.*

- **Why SQLite works here:** zero install (the JDBC driver bundles the native
  library), a single file the reviewer can open, and the `sqlite3` CLI ships with
  macOS and most Linux, so `src/main/resources/sql/queries.sql` runs directly. Window functions
  (SQLite ≥ 3.25) cover `LAG`/`LEAD`, ranking and medians.
- **What it costs:** no `median()`, `regr_slope()` or `date_trunc()`. So:
  - weeks are derived once on load (`week_start` = Monday) instead of per query;
  - median = middle row(s) via `ROW_NUMBER()`;
  - growth uses a **Theil–Sen** slope (the median of pairwise slopes) written in
    plain SQL. This is better than `regr_slope` would have been anyway, because it
    is robust to the outage week (§4.9).
- **At scale** SQLite is the first thing to replace (row store, single writer).
  See §7.

### 4.5 API framework: Spring Boot over Javalin / JDK HttpServer

- **Why:** it is what Java reviewers at a large telco expect; `MockMvc` gives
  clean controller tests; `ProblemDetail` gives idiomatic 400s.
- **Trade-off:** heavier than needed for one endpoint (startup ~2 s). It is kept
  minimal: `starter-webmvc` + `starter-jdbc`. No JPA, because the queries are
  analytical and `JdbcTemplate` is the honest tool. No Spring AI / LangChain4j,
  because one HTTP call does not justify a framework.

### 4.6 Part 3a: classification with a local LLM plus full human review

Pipeline:

1. **Normalise:** strip repeat-contact prefixes (recursively), giving 91 base
   texts. Record `followup_depth` per ticket.
2. **Classify** each base text once with Ollama `qwen2.5:7b` into the **agents' own
   taxonomy** (7 categories / 27 subcategories), so the two labellings are directly
   comparable. Each subcategory gets a one-line definition in `Taxonomy.java`
   (the agents work without one).
3. **Cache** to `output/note_topics_llm.csv`; re-runs only call the model for
   unseen texts.
4. **Review** all 91 texts by hand into `review/topic_review.csv`, kept separate
   from the model's output so neither overwrites the other. The final topic is
   the review; the model is scored against it.
5. **Compare** with the agent label per ticket → `output/classification_report.md`.

What we learned getting the model to behave (measured against the review):

| Attempt | Agreement | Change |
|---|---|---|
| category + subcategory as free strings | failed | 3B model mixed them ("Billing & Charging › Auto-renew unwanted") |
| one `topic` field constrained to an **enum** of valid labels, reason after | 71 / 91 | Ollama constrained decoding: no invalid labels possible |
| **restate the problem first**, then choose the topic | **81 / 91** | same model, prompt and taxonomy |
| larger `qwen3.5` for comparison | n/a | ignored the output schema; dropped |
| + written tie-breaking rules | 81 / 91 | errors moved, none net fixed; rules came from v1's errors |
| + all other reviewed labels as examples (leave-one-out) | 81 / 91 | same: a 3B model can't use 90 examples |
| + 8 most similar reviewed labels | 69 / 91 | word overlap picks look-alikes; model copies them |
| **same restate-first prompt on `qwen2.5:7b`** | **88 / 91** | nothing tuned; 86 / 89 on texts with one clear topic |

Every version, its raw output and its errors: `docs/experiments/classification/`.
Classification uses `qwen2.5:7b` (`cx.ollama.classify-model`); the brief keeps
`qwen2.5:3b` (`cx.ollama.brief-model`), whose bottom line already passes every check.
The 7B model needs ~5 GB of RAM, which is tight on an 8 GB laptop; reviewers without
it still get the committed labels.

**Ambiguous texts** are kept apart: `review/ambiguous.csv` lists each text that fits
more than one topic, with the candidates. A person decides them, they are not counted
as model errors, and they always go to `output/needs_human_check.csv` together with
texts the model and the review disagree on.

| Option | Pros | Cons | Verdict |
|---|---|---|---|
| Ollama `qwen2.5:7b` + review | Handles mixed Indonesian/English; 88 / 91 with no tuning; review makes final labels trustworthy | ~5 GB RAM, tight on 8 GB; needs Ollama to re-run (the committed cache removes that for reviewers) | **Chosen** |
| Ollama `qwen2.5:3b` (the PDF's example) + review | Runs comfortably on 8 GB | 81 / 91; prompt tricks did not raise it | Kept for the brief only |
| Keyword / TF-IDF + k-means in Java | Deterministic, zero deps | Clusters need manual naming; brittle with bilingual synonyms | Rejected (kept as an idea for scale, §7) |
| Free-tier cloud API | Best quality | Customer notes leave the laptop | Rejected |

**Why review every label:** with 91 texts it takes about 15 minutes, and it turns
"the LLM says" into a reviewed fact. The model's score (97% of tickets for 7B) is then the number
that tells us how far it could be trusted on unreviewed data at scale.

### 4.7 Part 2: anomaly rule, a rolling median ± 3 × MAD over the previous 8 weeks

For each week *w* of the filtered slice:

- `baseline = median(count[w-8 … w-1])`
- `spread   = 1.4826 × MAD(count[w-8 … w-1])` (MAD scaled to ≈ σ for normal data)
- `threshold = max(3 × spread, 0.25 × baseline, 5)`
- `anomaly = count[w]` outside `baseline ± threshold`, direction `UP` / `DOWN`
- no flag until ≥ 4 weeks of history exist.

| Alternative | Problem |
|---|---|
| Mean ± 2σ | One past spike (the July fiber cut) inflates σ and hides the next anomaly for 8 weeks. Median/MAD ignore it (pinned by a test). |
| Week-over-week % change | Explodes on small slices (5 → 10 = +100%) and flags the *recovery* after a spike. |
| Linear trend + residual | Needs more than 26 weeks to be stable; harder to explain to a non-technical reader. |
| STL / Prophet | Overkill, no seasonality to model in 26 weeks, new dependency. |

The floors (`25% of baseline`, `5 tickets`) stop tiny slices from flagging noise
when MAD ≈ 0.

**Whole weeks:** `from` snaps back to its Monday, `to` forward to its Sunday, and
the result is clipped to the data range, so no partial weeks and no fake "drop"
to zero after the data ends. The 8 weeks *before* `from` are read for the
baseline, so a narrow range is still judged correctly.

**Known incidents:** each week lists incidents active that week **or that ended
the week before** (`relation: during | previous_week`). The second case was added
after a test failed on real data: the week after the fiber cut is legitimately
anomalous (follow-up contacts, F1b), and without the link it looked unexplained.

### 4.8 Part 3b: facts in code, template body, LLM only for the opening

1. `BriefFactsBuilder` computes `brief_facts.json` for the last 4 weeks against the
   previous 8, using the **corrected** topic, with explicit rules:
   - **escalate:** ≥ 25% up, ≥ 20 extra tickets/week, Poisson z ≥ 4 (well beyond
     chance across 27 topics), not explained by an incident;
   - **watch:** ≥ 20% up with z ≥ 3 but small; says whether it is within the range
     seen earlier in the year;
   - **explained:** a Network Quality rise concentrated in an incident's region;
     every incident in the window checked for actual impact (INC000004: none);
     earlier spikes (≥ 100 extra tickets) listed with their cause, or flagged as
     having none;
   - **process:** SLA breach now vs baseline, to separate chronic from new.
2. `BriefTemplate` renders the facts deterministically.
3. The model writes only the **Bottom line** (≤ 70 words) in a fixed shape: the
   problem with its numbers and why it is real, the ask ("Assign a PIC to find the root cause and report
   back next week", required word for word), and that everything else is explained. It is accepted only if
   every number appears in the facts (`NumberGuard`), every escalated topic is
   named without its category prefix, it has no filler ("please", "promptly",
   "address this issue"), and it is plain sentences; otherwise the template
   sentence, which has the same shape, is used. The model sees topic names with
   the category prefix stripped, because it kept copying "Billing & Charging > …"
   verbatim. The first version passed every check but read as "Please review and
   address this issue promptly", which asks an executive for nothing specific.

*Originally the model rewrote the whole brief.* That version passed the number
guard yet changed meaning ("compared to the baseline of 3.9" when 3.9 is the
all-ticket average; a comparison dropped; a key phrase lost). A number check
cannot catch that, so the body went back to the template
(`docs/experiments/full-llm-brief.md`). The judgment was always in code; now the
wording of the body is too.

| Option | Pros | Cons |
|---|---|---|
| **Template body + LLM bottom line + guards** (chosen) | Fluent where it matters; short enough to verify | Body prose is plainer |
| Full LLM rewrite + number guard | Reads best | Meaning drift the guard can't detect |
| Template only | Fully deterministic | No use of the model the assignment invites |

### 4.9 Part 1: SQL interpretation choices

1. **Weekly volume per 1k subscribers:** Mon–Sun weeks; full week × category ×
   region grid so zero weeks show as 0.
2. **SLA breach:** defined only for High priority (> 60 min). Low/Medium show
   `breach_rate_pct = NULL` ("no SLA defined"); the share over 60 min is shown
   for all priorities as context.
3. **Repeat contact:** a ticket counts if the *same subscriber* raises another
   within (0, 7 days]. Tickets from the final 7 days are excluded from the
   denominator (right-censored). Also reported: the note-prefix follow-up share.
4. **Fastest growing vs large-but-flat:** Theil–Sen slope ÷ median weekly volume
   (%/week), plus last-4 vs previous-8 ratio. Only categories growing ≥ 1%/week are
   called "fastest growing". In this data that is Billing & Charging alone, so the
   other two top-3 entries are labelled "within noise" rather than presented as
   winners. Q4b shows the rise is one subcategory.

## 5. Testing

37 tests, `./mvnw package` runs them all.

| Layer | Test |
|---|---|
| `AnomalyDetector` | Parameterised: flat, spike, drop, noisy wobble, small-slice floor (both sides), large-slice relative floor; an earlier spike does not mask a later one; no verdict under 4 weeks; only the previous 8 weeks count. |
| `NoteNormalizer` | Each prefix, nested prefixes, case, whitespace, no false strip on legitimate commas. |
| `Csv` | Quotes, escaped quotes, commas and newlines in fields, CRLF, empty last field; escape round-trip. |
| `BriefWriter.check` / `NumberGuard` | Accepts fact numbers (with thousands separators); rejects invented and rounded numbers, dropped topics, long or list-shaped text; list markers are not figures. |
| `TrendController` (MockMvc, real data) | July outage week flagged with `INC000001` (`during`), following week flagged with it as `previous_week`, then normal; narrow range still gets a baseline; case-insensitive filters; 400s for bad date, `from > to`, unknown region; out-of-range dates give an empty result. |
| `BriefFactsBuilder` (real data) | Escalates exactly one topic (+70%, 6 of 6 regions); INC000004 "no measurable effect"; 13 Jul spike attributed to INC000001; Email SLA reported. |

## 6. Deliberately left out

- **Authentication, Docker, CI:** not asked for; each adds reviewer setup time.
- **Per-agent analysis:** the data has no agent ID.
- **CSAT modelling:** ~70% empty; used only descriptively.
- **Second reviewer / Cohen's κ** for the 91 labels: the right next step before
  using the findings for agent coaching.

## 7. Where this breaks at 5 million tickets

| Component | At 42k | At 5M | Change |
|---|---|---|---|
| Rebuild SQLite from CSV at start-up | ~1 s | minutes; row store; single writer | Build offline into a columnar store (DuckDB/Parquet or the warehouse); API reads a pre-aggregated `weekly_counts(category, region, week)` table. |
| `/trends` aggregates raw tickets per request | ms | 100s of ms | Same pre-aggregate (tiny at any scale); cache per filter. |
| Classification | 91 unique texts | real notes are mostly unique; ~0.6 s/note on CPU ≈ 35 days | Embeddings + small classifier trained on reviewed labels; LLM only for low-confidence notes; sampled human review to measure drift. |
| Repeat-contact window query | fine | big sort by subscriber | Columnar engine; incremental by month. |
| Incident attribution | 4 incidents, weekly overlap | many incidents | Interval join at site/cell level, hourly. |
